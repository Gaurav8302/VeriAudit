# Demo Flow

The exact judge-facing path. Per the source of truth §2, the audience must
**experience the problem before seeing the solution**, and the climax is the boss
question — not the cryptography.

```text
AI performs audit → three months pass → history becomes crowded
→ "Why did the AI make this decision?" → search → exact historical audit
→ execution trail → evidence + AI actions + human review → CooL verification
```

Target run time: **4–5 minutes**.

> **Milestone 6A status.** Backend stages and the demo state machine are
> built (`lib/demo`). Screen states map 1:1 to `DEMO_STATE_MACHINE.md`.
> The visual guided demo lives at `/demo`. The public landing is `/`.
> After the final demo screen, **Explore the product** enters `/product`.
> That product workspace is documented in [PRODUCT_APPLICATION.md](PRODUCT_APPLICATION.md).

`CONFIRMED`: all four scenarios run on the same engine and are live behind
`GET /api/audits` and `POST /api/audits/run`. They produce real audits with

CooL receipts it does not hold. Live runs of any scenario seal the canonical
nine events when CooL is available.

## Stage 3 — AI performs the audit

| | |
|---|---|
| **User action** | clicks **Run audit** |
| **UI state** | staged progress, each line resolving as its events are sealed — **not** a fake spinner |
| **Backend** | `POST /api/audits/run` (Node runtime): engine tests 12 controls → event manager builds 30 events → CooL adapter seals the 9 canonical ones against the rehydrated log. `CONFIRMED` working |
| **Data** | 4 artifacts → 12 control results → 3 findings → 3 reviews → 1 conclusion |
| **CooL** | 9 × `cool.record(...)`, ~150 ms total (`CONFIRMED` ~17 ms/record). Returns receipts + updated `logState` |
| **Expected result** | the six stages complete, each showing the count of CooL receipts sealed |
| **Determinism** | **the result is computed, not generated by an LLM.** Always 12 tested / 9 passed / 3 exceptions |
| **Failure handling** | if `record()` throws, the stage shows *"evidence unavailable"* and the audit still completes with `cool: null` — the audit never fails because sealing failed |

```text
Evidence loaded              ✓  4 artifacts
Documents parsed             ✓  4 parsed
Relevant evidence retrieved  ✓  7 passages
Controls tested              ✓  12 tested · 9 passed · 3 exceptions
Finding generated            ✓  3 findings
Human verification requested ✓  routed to J. Okafor
```

Each ✓ that has a receipt shows a small **sealed** marker, so CooL is visible
from the first minute rather than only at the end.

## Stage 9 — Execution trail

| | |
|---|---|
| **User action** | clicks **Execution trail** |
| **UI state** | the nine-node causal spine, left to right / top to bottom, with counts collapsed onto stage nodes. Each node shows type, actor (AI / human / system), logical time, and its integrity chip |
| **Backend** | `GET /api/audits/:id/events` returns nodes, 29 parent edges, and `spineEventIds` — the layout does not have to be derived in the UI |
| **Data** | 30 events linked by `parentEventId`, collapsed for display (`EVENT_MODEL.md` §3) |
| **CooL** | 9 nodes show *sealed*; collapsed stage nodes show how many of their events are backed |
| **Expected result** | the judge can read *why* the finding happened by following the chain |
| **Determinism** | fixed layout, fixed node set. `CONFIRMED` — same 30 event ids every run |

```text
Source Evidence → Retrieval → Model Execution → Control Test
  → Finding → Human Review → Final Conclusion
```

This is the hero UI. It must be legible without explanation.

`CONFIRMED`: `spineEventIds` is computed by walking `parentEventId` from
`conclusion.created` to the root, and it returns exactly the nine sealed events
in exactly the order above. The trail the judge reads and the trail that is
cryptographically backed are the same trail — there is no unsealed step in the
middle of the reconstruction.

## Stage 11 — CooL verification

| | |
|---|---|
| **User action** | clicks **Verify** on `finding.created` |
| **UI state** | compact panel first, technical detail on expand |
| **Backend** | `POST /api/audits/:id/verification` with the caller's receipts (or `POST /api/cool/verify` for one) → `withTrustedKeys` → `verifyEvidence` with `expectedMeasurement` → `key_id` allow-list → `inclusion === "pass"`. `CONFIRMED` 9/9 verified |
| **Data** | the ~30 KB receipt from IndexedDB |
| **CooL** | the real verification. Measured ~1 ms server-side |
| **Expected result** | **VERIFIED**, with `simulated` shown honestly for the two hardware domains |
| **Determinism** | a valid receipt always verifies |
| **Failure handling** | any failure shows the SDK's own `reasons[]` verbatim |

```text
Execution Integrity                          VERIFIED

✓ Binding            content hash recomputes
✓ Signature          ML-DSA-65 + Ed25519 both verified
✓ Inclusion          leaf 6 of tree 9, audit path reconstructs the signed head
✓ Evidence integrity commitments match the stored artifacts
✓ Signer             cool-enclave-70a788d680 (published VeriAudit key)
~ Attestation        simulated — no hardware root of trust
~ Enclave            simulated
– Witnesses          none (no external witness infrastructure in this build)
– Anchor             none (never submitted to a public chain)
```

The `~` and `–` rows are deliberate. The vendor's `HACKATHON.md` is explicit that
`attestation` and `enclave` read `simulated`, never `pass`, and that blurring
that distinction defeats the project's purpose. Showing them earns more credit
than hiding them.

## Stage 12 — Tamper demonstration (P1)

| | |
|---|---|
| **User action** | clicks **Show tamper demo** |
| **UI state** | side-by-side. Left: the original finding, *3 exceptions*, **VERIFIED**. Right: the same receipt with the story altered to *0 exceptions* |
| **Backend** | `POST /api/cool/verify` on the mutated receipt |
| **Data** | an in-memory copy; the stored receipt is never modified |
| **CooL** | real verification of a real mutation |
| **Expected result** | **VERIFICATION FAILED** with the SDK's actual reasons |
| **Determinism** | `CONFIRMED` across 18 mutation cases |

```text
Original:  3 exceptions   Integrity: VERIFIED
Altered:   0 exceptions   Integrity: VERIFICATION FAILED
  binding    FAILED — recomputed binding_hash does not match the receipt
  signature  FAILED — ML-DSA-65 and Ed25519 did not verify
```

Two mutations are offered, because they fail differently and the contrast is the
teaching moment:

1. **Edit the finding** → `binding` and `signature` fail.
2. **Delete an event from history** → `verifyConsistency` returns `false`
   against the STH stored when the audit was sealed. `CONFIRMED`.

The second is the stronger demo: it shows that *removing* an inconvenient record
is detectable, not just editing one.

## Failure handling summary

| Failure | Judge sees | Never |
|---|---|---|
| `record()` fails | *"evidence unavailable"* on that event; audit completes | a silent gap |
| Verification fails | **FAILED** + real domains + real reasons | "VERIFIED" |
| Receipt not in session | *"receipt not in this session"* + offer to re-run | "FAILED" |
| Search returns nothing | suggestion chips | a dead end |
| Cold start / clean browser | the flow simply starts at Stage 1 and regenerates everything | a broken session |

Per guideline §15: never report VERIFIED when verification did not happen.
